# 里程碑二工程复审与运行规则

## 开发、编排和复评

- 阶段 2A、2B 重跑时指定全新的输出目录。历史请求账本、候选评估和冻结清单保留原样。比较不同运行时按模型、种子、评测预算和请求上限配对。
- 规划、试跑、续跑和失败重试共用请求上限。以已发起的请求数核对上限，另列成功响应、Token 和墙钟时间。旧五臂实耗有超额，历史对照只能作为探索性数据。
- 原有 `algorithm-optimization` Skill 通过 `session submit-plan → execute → collect → finish-round` 编排，EoH 搜索已选接口中的 Hook。执行和收集都会核对计划回执与接口内容的哈希。先检查继承代码的身份和接口，再把可兼容的候选送入搜索。切换接口后的基线回退见 `interface_seed_receipt.json`，冻结前的候选五关复验见 `winner_validation_report.json`。
- 冻结求解器复评使用隔离子进程和父进程看门狗。求解器内部预算由各模板检查，验证器独立验解。报告另列完整完成率、可行返回率和迭代上限次数，旧字段保留历史口径。新增版本的公共题集同步算法目录与路线，盲测只保留许可公开的结果和派生特征。

## 盲测与发布

1. 由独立保管方把新题集存入仓库外受限目录，并将公开承诺与私有实例分离。仓库外路径是代码检查，访问隔离由保管方账户和文件权限落实。
2. 在新输出目录运行 `tools/run_phase2c_blind_and_release.py --freeze-only --out-dir <新目录> --commitment-path <公开承诺>`，独立保存返回的 `protocol_sha256`。计划绑定公开承诺、基线和已冻结的候选内容。使用新 2B 产物时，为每份归因或预算档的 `archive_manifest.json` 传入一个 `--phase2b-archive`，评测时使用同一组清单。
3. 在最终评测时使用同一目录及公开承诺，传入 `--protocol-sha256`、`--sealed-path` 和全新 `--release-id`。开封前登记一次性执行记录，已消费的承诺保留历史账本。当前 M2 盲测已完成。
4. 如果评测完成后打包失败，使用相同目录、已打印的 `--publish-from-sha256` 和未发布的 `--release-id` 恢复。新版本先构建和校验，再切换 `current`。存在的发布 ID 保留原样。

## 论文证据口径

- 500 ms 历史双种子实验中，LLM 诊断组在 `select_64` 第一（20.8618），盲测第三（24.2306）。固定强接口和 Racing 的盲测均长分别为 24.2039、24.2274。LLM 组历史请求少于 Racing，固定逐点组的平均请求更少。
- 25 ms 下，确定性规划组由动态合并切到静态合并。与直接迁移相同组的 500 ms 动态合并求解器相比，预算耗尽由 40/120 降到 0/120。LLM 组在两个预算都选静态合并，直接迁移其 500 ms 最优种子也是 0/120 耗尽。
- 实例配对显著性针对已冻结的求解器；两个搜索种子不足以支持普遍优于固定强接口或 Racing 的主张。历史报告中的零 p 值源自有限精度或重采样计数，引用时注明方法与精度。
- 跨宿主主张以共享 Skill 和 Session 合同为限。当前工程回归走本地 mock；每个外部宿主的真实运行与硬请求上限下的在线五臂实验需要独立证据。
