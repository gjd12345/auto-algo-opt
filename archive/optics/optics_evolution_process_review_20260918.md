2026-09-18。统计快照：20:45 香港时间。本文先复盘，不实施修复、不追加实验。

## 结论

**已经证明系统能生成、评测并改善光学处方；尚未证明它能高效地组织全局搜索。** 当前最明显的问题是：Plan 长期停留在很小的局部邻域，Execute 多次重复或未实现所声称的机制，Evaluate 把微小改善当成继续同一方向的充分理由。Memory 已有真实写入和消费，但消费链路不稳定，且记录数量不能代表决策质量。

因此，现在不能把提升有限直接归因于任务允许的搜索空间太小，也不能据此判断 Luna 或生成模型能力不足。应先修复和验证搜索组织方式，再讨论扩大任务边界。

最早大批次 170 个候选只有 **66 个不同处方 hash**，104 次属于批内重复，重复率约 **61.2%**。继续运行的 cont 批次也只有 7 个不同 hash；早期重复 parent 的请求没有提供新的机制证据。

从 0.5552282993 到当前 0.5589922062，增加约 0.00376391，即约 0.68%。这是实质提升，但不足以说明持续追加同类请求有很高收益。

值得区分的三个问题：

1. **机制没有落地与机制无效不是一回事。** 请求返回相同 parent 时，不能把该轮解释成“尝试了新机制但没有改善”。
2. **补偿方向需要以实际诊断核验。** bending 路径出现过焦面补偿方向问题；后续纠正能够恢复可行，说明执行一致性比继续润色机制名称更重要。
3. **封存时机影响 Memory。** 既有 bending 报告留下了封存后不能写入的记忆草稿。它不是 Runtime 已发布记忆。approach 则有读取记录但没有生成请求注入，不能仅凭读取宣称已消费。

此前报告的 T1 最佳 0.5587570542 对当时批次成立；本次发现后续 approach 的 0.5589922062，应更新当前最佳，但不能继承旧处方的审计或 verifier 结论。

这支持“**Plan 主动限制了实际探索范围**”，但不证明未尝试变量一定更好；更不能据此放宽 task bounds 或评测约束。

### 4.2 后期小幅改善掩盖了停滞

批次 13 连续把 stop 步长减半：0.0015625、0.00078125、0.000390625 mm。最后一步 Q 仅增加约 0.00001685。

“连续若干轮无改善才换机制”在这里不起作用：每轮都有极小正增益，就可以无限延续同一局部方向。应区分局部抛光有效与全局搜索有效。当前的正增益尚不能抵消探索覆盖不足这一事实。

### 4.3 关键约束并不始终是焦点

33 条成绩记录中，失败约束出现次数包括 MTF40：19、focus：10，MTF10/MTF20/RMS 各 7；这些计数重叠。

当前最佳的最低 MTF40 约为 0.01004940，门槛 0.01，余量仅约 0.00004940；focus error 约 0.034741，允许界限 0.15。因此，当前 incumbent 的主要脆弱边界更像 MTF40，而不是仍需一味校焦。

批次 07 曾出现 Q≈0.292601 但焦点不合格的候选；后续恢复焦点后 Q≈0.147097，又因 MTF40 失败。它们说明必须分析多约束耦合，不是“曾找到 0.29、被框架错误拒绝”。可行性优先的接受规则应保留。

“版本数”不是不同知识数，“读取记录”不是有效利用数，“注入请求”也不证明因果收益。

新 T3 有 6 个已选择 Memory 的请求没有完成实际注入。早期上下文体积限制和降级路径确实打断了链路；后期批次 09 起有明确正文注入，但仍未产生明显机制突破。不能再简单说成“Memory 完全没有写入”，也不能说成“已经完全解决”。T1 cont 与 Grok 分支同样存在真实注入，不能把新 T3 后期的修复称为整个系统首次消费成功。

应分别审查两个消费者：

- 宿主 Agent 读了什么，并因此怎样改变 Plan；
- 内层生成请求实际获得了哪些版本和正文。

目前第二条已有计数，第一条的决策增量更难证明。大量 insight 如果只是“再把 stop 减半”，可能只是把局部轨迹文字化，并没有帮助跳出局部搜索。

当前工作树中的 `runner.py` 已存在未提交的上下文压缩改动：先压缩诊断/最近反馈，再必要时清空 Memory。它与部分历史运行版本不同。**历史注入丢失是已观察事实；当前改动是否彻底修复，不能用旧请求结果判断，也未在本次重新验收。**

## 6. Plan、Execute、Evaluate 各自需要承担什么责任

|层|已观察问题|不能混淆的解释|
|---|---|---|
|Plan|变量覆盖窄；越来越小的单轴步长；批次过短|合法 Plan 不代表有信息增益|
|Execute|重复 parent；部分机制与实际 delta 不符；上下文退化|没执行该机制，不等于该机制失败|
|Evaluate|持续用微小改善支持原方向；约束瓶颈切换分析不足|接受更优 incumbent 正确，但继续同一搜索方向未必正确|
|Memory|选读、注入与改变决策之间有断点|写了很多不代表学到了更多|
|调度/监督|多目录多批次；deadline/上下文造成中断；重复重评与审计|更多 Session 不等于更多有效探索|

监督侧也需要改进：发送指导消息不代表 Luna 已经采用；任务切换后必须确认当前 run、工作目录和安装身份；不能只汇报微小新高而忽略收益递减。本次仅暂停自动派发和请求执行任务停止新增工作，没有强行修改历史 Session 的状态。

## 7. 下一步修复讨论清单——本次不执行

建议先讨论并收敛下面三组，而不是继续堆功能：

### 第一组：让闭环事实足够可信

1. 每轮明确显示“Plan 要改什么 → 实际改了什么 → 哪条约束改善/恶化”，重复或未实现单列，不能归类为机制失败。
2. 定义有界上下文的必留字段，以及 Memory 省略原因；验证宿主选读、Plan 引用、生成端注入三段链路。
3. 用当前工作树与各安装版本做身份核对，避免旧实验、新源码和未提交补丁混为同一实现。
4. 先保留证据再收口超时/中断；避免通过开新 Session 隐藏失败原因。

### 第二组：修正搜索组织，而不是改变评测标准

1. 用有效改善幅度、单位评测收益和变量/机制覆盖共同判断停滞，不仅检查是否出现严格正增益。阈值应结合重复评测稳定性确定，不能随意指定一个百分比。
2. 将局部抛光与探索分开预算；保留当前 best，但不让所有请求继续围着同一个 stop 微调。
3. Plan 应提出可区分的假设及失败判据，Execute 校验处方差分；不要强制每轮无差别改变所有变量。
4. 减少过短批次产生的初始化、重评与审计开销，同时保留全局期限、UNKNOWN 和封存边界。

### 第三组：用受控实验判断改动是否值得

先用最小离线用例核验 delta 分类、上下文消费与状态收口，再讨论授权后的真实小批次。比较应固定任务与物理身份、起点和总 online 评测预算，报告可行率、重复率、有效改善/评测以及 wall time。

数值优化器可作为同协议对照：让 LLM 负责机制、变量耦合和搜索区域，让确定性数值搜索处理连续参数，是值得验证的假设；但本报告不据此直接替换现有执行器，也不宣称 CMA-ES 必然更优。

**建议先修“执行一致性 + 反馈/Memory 实际消费 + 停滞判定”，再恢复有限、可比较的搜索批次。** 不修改约束、评分或独立审计规则，不用新实验掩盖尚未解释的旧证据。
